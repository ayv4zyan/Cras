# Supabase is the sole backend platform

Cras MVP uses one hosted **Supabase** project as its entire backend platform and serves many Operators from one public Deployment. Postgres is the system of record, Auth plus RLS form the identity and authorization boundary, the Data API supports client CRUD, Realtime carries live changes, Storage is available for blobs, and Edge Functions host operations that need secrets or trusted server-side logic. Every Operator's data must be isolated from every other Operator. There is no separate Cloudflare deployment, Hono API, Hyperdrive connection, Durable Object, or custom Operator API token.

The web deployment and Android build contain the Supabase project URL and publishable key and act with the Operator's user JWT. Google is the only MVP authentication provider: web uses browser OAuth, Android uses native Google Sign-In, and any Google account may register. A secret / `service_role` key must never ship in web or Android. A dedicated `api` schema is the only client-facing Data API surface: canonical Task reads use `security_invoker` views, Task commands use narrowly scoped `security_invoker` RPCs with version CAS, and canonical resources without Task mapping use direct CRUD or read-only access. Database-triggered private Broadcast events identify the changed resource, id, operation, and relevant parent id so clients can refetch precisely. Edge Functions are reserved for provider secrets, external calls, or trusted orchestration. Details: [Which operations use Supabase Data API vs Edge Functions?](https://github.com/ayv4zyan/Cras/issues/26).

Every Operator-owned row—including Tasks, Labels, Comments, Settings, and Task–Label joins—carries a non-null, immutable `operator_id` that defaults to `auth.uid()`. RLS permits ordinary reads and mutations only when that identity matches the caller, and rejects forged inserts or ownership transfers. Composite foreign keys include `operator_id`, so Subtask parents, Comments, and both sides of Task–Label joins cannot cross Operator boundaries; database constraints also preserve one-level Subtasks and one Settings row per Operator. Deployment configuration and the Voice model catalog remain authenticated read-only data for Operators and are changed only by migrations or narrowly scoped trusted Deployment operations; there is no MVP admin UI. Realtime follows `SELECT` RLS, Postgres RPCs use caller permissions by default, and Edge Functions validate the JWT and derive the Operator identity rather than trusting client input. `service_role` is never a general path to Operator data. The spec requires isolation integration tests with two Operators and an unauthenticated client across tables, relationships, Realtime, RPCs, and Edge Functions. Details: [How is each Operator's data isolated?](https://github.com/ayv4zyan/Cras/issues/27).

Voice capture uses one authenticated Edge Function as its provider boundary. One Deployment-wide DeepInfra credential lives only as an Edge Function secret. The function orchestrates speech-to-text plus structured extraction; clients upload mono 16 kHz PCM WAV, and the function validates rather than transcodes. Supabase also holds a Deployment-managed **Voice model catalog**, seeded by Cras migrations; Operators may read enabled choices, but only the Deployment maintainer may change them. Shared Operator **Settings** stores nullable stable catalog keys and an optional custom extractor prompt. Null inherits the current Deployment default: Voxtral Small for speech-to-text and Gemma 4 26B-A4B-it for extraction. The Edge Function resolves Settings against the current catalog and validates the effective models before calling DeepInfra; a disabled stored choice falls back to the current default. Server-side audio and transcripts are never retained.

Public Voice capture is Deployment-funded but bounded. Each request is at most two minutes and 4 MB. The default per-Operator Voice allowance is one active request, three requests per rolling minute, 20 requests and ten audio minutes per rolling 24 hours, and 300 requests and 60 audio minutes per rolling 30 days. The Deployment circuit breaker stops new Voice capture at either $1 per rolling 24 hours or $5 per rolling 30 days; an independently controlled `voice_enabled` setting can also stop new capture. Server time defines every window. Values are maintainer-adjustable Deployment configuration, apply immediately to new reservations, and require no MVP admin UI. DeepInfra automatic top-up remains disabled and its spending limit is the final independent backstop.

The Edge Function rejects authentication, format, size, and duration failures before charging allowance. Immediately before the first provider call, trusted accounting atomically reserves one request, the validated audio duration, and conservatively estimated spend. At most two internal retries are permitted for transient 429, timeout, connection, or 5xx failures; they do not double-charge the Operator. Provider-bound failures retain allowance and uncertain spend until reconciled. Completed calls reconcile against measured duration and returned token counts. A later client retry is a new request. If accounting cannot reserve safely, Voice fails closed while ordinary Task features remain available.

Usage-security records contain only a keyed pseudonymous identity, time buckets, aggregate requests and audio seconds, provider-attempt category, model catalog key, token counts, cost, and reservation state. They never contain email, raw Google identity, Tasks, recordings, transcripts, prompts, Drafts, or provider responses. Detailed buckets expire 35 days after their end; after permanent account purge, the pseudonymous key remains only while an associated unexpired bucket exists, so re-registration cannot reset an active allowance. Details: [How is shared AI usage bounded?](https://github.com/ayv4zyan/Cras/issues/29).

Supabase also holds **Deployment configuration** for shared domain defaults. Its `default_timed_plan_type` is seeded as `instant`, readable by both clients, and writable only by the Deployment maintainer. Operator Settings adds nullable `default_timed_plan_type`; `null` or a missing Settings row inherits the Deployment value, while `instant` or `floating` pins an explicit Operator override. The effective default applies whenever a Task becomes timed without an explicit type: creating a new timed Task or adding a clock time to an untimed/Date-only Task. It never rewrites an already timed Task, whose existing type is preserved unless explicitly changed. Both clients cache the effective value for offline use and fall back to Instant before any value has been cached. Voice follows the same boundary: only an explicit spoken Instant/Floating instruction overrides the default; contextual wording does not. Details: [Where does the Instant vs Floating default live?](https://github.com/ayv4zyan/Cras/issues/21) and [How does Voice capture choose Instant vs Floating?](https://github.com/ayv4zyan/Cras/issues/22).

Account deletion is recoverable for exactly seven days. After fresh Google reauthentication and explicit confirmation, every session is revoked and the Operator enters Pending deletion; all client-facing Supabase paths must deny ordinary access even while an issued JWT has not expired. Recovery uses the same Google identity. At the deadline, a trusted purge hard-deletes the Auth identity and all Operator-owned data; the same Google identity may later register as a new empty Operator. Details: [What happens when an Operator deletes their Cras account?](https://github.com/ayv4zyan/Cras/issues/28) and `docs/adr/0006-recoverable-account-deletion.md`.

The relational decisions remain: one row per Task; Labels plus a join table; Comments as child rows; Subtasks via `parent_id`; version compare-and-swap for overlapping writes; Outboxes on both web and Android; no merge UI.
